# SignalDB Architecture Reference

## FDAP Stack

SignalDB is built on Flight, DataFusion, Arrow, Parquet (explained with
external references in `docs/architecture/fdap.md`):

- **Flight**: Apache Arrow Flight for zero-copy inter-service gRPC communication
- **DataFusion**: SQL query processing engine (used by Querier)
- **Arrow**: In-memory columnar format used throughout the entire pipeline
- **Parquet**: Persistent columnar storage via Iceberg table format

**Critical rule**: Always use Arrow/Parquet types re-exported by DataFusion to ensure version compatibility:

```rust
// CORRECT
use datafusion::arrow::array::StringArray;
use datafusion::parquet::arrow::ArrowWriter;

// WRONG - version mismatch risk
use arrow::array::StringArray;
```

## Write Path

```
OTLP Client (gRPC :4317 / HTTP :4318)
    -> Acceptor (validates auth, enforces rate limits + storage quotas, converts OTLP->Arrow, writes to WAL)
    -> Writer via Flight do_put (transforms v1->physical-v3 schema, writes to the batch tenant's own WAL)
    -> WalProcessor (background, 5s interval)
    -> Iceberg Tables (Parquet files in object store)
```

Key details:

1. Acceptor writes to WAL before acknowledging client (every WAL record is length-framed + CRC-32 checked, `common::wal::framing`; a corrupt record is quarantined and skipped, never poisons its segment). Acceptor and writer alike hold one WAL per `(tenant, dataset, signal)` via `common::wal::manager::WalManager` (#932), so the blast radius of a poisoned segment or a slow flush is one tenant
2. Acceptor converts OTLP protobuf -> Arrow RecordBatches using Flight schemas (v1)
3. Writer transforms v1 Flight schema -> physical-v3 Iceberg schema (field renames, type conversions, computed partition fields, materialized `label_<key>` columns for configured attributes across all four signals, allowlists resolved per tenant (tenant schema override replaces the global set); new tables (all signals) store attributes as typed `Map<String,String>` columns for exact any-attribute matching). `schemas.toml` is the physical schema source of truth for all six built-in table types (traces, logs, all five metrics representations, profiles) — `iceberg::schemas`'s `create_*_schema_with()` functions resolve from it rather than building field lists by hand. On every load (not just creation), `ensure_table` also brings an existing traces/logs table's schema forward to schemas.toml's current version if it's behind (`common::iceberg::evolution::ensure_schema_current`) — additions-only when the table's starting version isn't trusted (no recorded `signaldb.schema.version`, or one not found on the version chain), renames/removals also enabled when it's a known recorded version walked hop by hop — metrics/profiles resolve from `schemas.toml` for creation but aren't covered by this evolution path yet.
4. Writer's `do_put` acks after its WAL flush (it does NOT commit synchronously); WalProcessor reads WAL entries every 5s (exponential backoff on failure) and writes Parquet via DataFusion, coalescing commits per `(tenant, dataset, table)` (`[writer].commit_interval` / `max_uncommitted_rows`) to cap the Iceberg/catalog write rate. Data is queryable once committed; `do_action("flush")` forces an immediate commit (read-your-writes)
5. Processed WAL entries are marked and cleaned up
6. `WalManager`'s per-tenant WAL cache is bounded: idle eviction alone can't bound an actively-written fleet, so a soft `[wal].max_instances` cap (default 256) also evicts the least-recently-appended drained, unreferenced WAL on a cache miss, never failing a write to honor it

Every signal table declares a time-leading Iceberg **sort order** (traces `(timestamp, trace_id)`, logs `(timestamp, service_name, severity_text)`, metrics `(timestamp, metric_name, service_name)`, profiles `(timestamp, service_name)`), set at creation and added to older tables by `ensure_table` on load. The declaration is intent; per-file honesty is a fact carried in the file's own Parquet footer (`sorting_columns` + `iceberg.sort-order-id` → manifest `sort_order_id`), and the DataFusion provider claims the ordering only for attested files — so an unattested file in range keeps the explicit sort rather than corrupting an ordered result. Attesting an unsorted file yields wrong results, not slow ones. Both producers go through one shared decision (`common::iceberg::sort::write_sort_key`): ingest sorts each commit group before writing, compaction sorts by the declaration rather than its own key list. See `storage-layout` skill and `docs/architecture/storage-layout.md#declared-sort-order`.

Alongside the WAL loop the writer runs a **table reconciler** (`src/writer/src/reconcile.rs`): a startup pass plus one every `[writer].table_reconcile_interval` (default 5m, `0s` = startup only) over the tenant registry, ensuring every registered tenant/dataset holds a table for each signal type enabled for that tenant — including a tenant's `default_dataset` when no dataset row names it, which the registry guarantees is in `ResolvedTenant.datasets` regardless (`catalog_manager.rs::ensure_default_dataset`). It needs a tenant source on the writer's `CatalogManager` (attached in both `writer/src/cli.rs` — the `signaldb writer` entry point — and `signaldb-bin/src/main.rs`, which start the loop independently). Provisioning goes through the same `CatalogManager::ensure_table` the write path uses, so failures are warn-level and degrade to create-on-first-write. Correspondingly, the querier reads a missing signal table as empty rather than erroring (`query/table_lookup.rs`). The router's tenant self-service `GET /api/v1/tenants/{id}/tables` (`common::schema::TenantSchemaRegistry::list_tables_for_tenant`) reads the catalog the same way, grouped by dataset, so what a reconcile pass or an on-demand `POST …/tables/create` actually created is directly observable. The router's dataset-creation endpoints (management and admin APIs) also call `CatalogManager::ensure_dataset_tables` synchronously, best-effort, right after the dataset row commits, so a new dataset is usually queryable immediately rather than waiting for the next reconcile pass; a failed attempt there just falls back to the reconciler.

## Query Path

```
HTTP Client (Tempo / Pyroscope / Loki APIs)
    -> Router (:3000 HTTP, :50053 Flight)
    -> Querier via Flight do_get (:50054)
    -> DataFusion SQL against Iceberg tables
    -> Parquet files in object store
    -> Results stream back as Arrow RecordBatches
```

Key details:

1. Router validates auth, discovers Queriers via `QueryExecution` capability
2. Flight tickets encode query type + tenant context: `find_trace:{tenant}:{dataset}:{trace_id}[:{start}:{end}]` (optional unix-second time hints). Single-trace lookups prune Parquet row groups via the `trace_id` bloom filter (min/max stats never prune a high-cardinality point lookup); see the `storage-layout` skill's Parquet bloom filters note
3. Querier uses `TenantCatalog` to bridge DataFusion 3-level model to Iceberg 2-level namespace
4. Results stream back as Arrow RecordBatches via Flight (trace not found -> Flight `not_found` status). HTTP responses also return the server span's trace context and stage timings (`Server-Timing`/`traceresponse`; see `docs/users/response-trace-context.md`). Query wall-clock is bounded by the querier's `query_timeout`; the caller's Flight per-request deadline is derived from it plus a grace margin so the callee's `deadline_exceeded` (HTTP 504) wins over an opaque client-side `cancelled`
5. Standalone querier also serves Tempo's `tempopb.Querier` gRPC protocol on the Flight port (see `tempo-api` skill)
6. Router also nests query APIs for every signal, each lowering a parsed query to a DataFusion `Expr`/aggregate over the signal's Iceberg tables (never a SQL string, matching the trace path). **Parsing and lowering are separate crates**: `logql` and `traceql` (published as `logql-parser`/`traceql-parser`) lex, parse, and syntax-check with `thiserror` as their only dependency — no Arrow, no DataFusion, no workspace crate — so query validity depends on the query text alone and never on a tenant, catalog, or promotion state. Since `ir-single-lowering`, TraceQL and LogQL no longer have their own dedicated lowering to a DataFusion plan: `ql_ir::{traceql_to_ir,logql_to_ir}` lowers the parsed query to a query-IR document, and `querier::query::ir_planner::plan_document` — the same planner `POST /api/v1/query` uses (point 81 below) — lowers that document the rest of the way. Each compat surface's own `querier/query/{logql,logql_metric,search_filter}.rs` now holds only what's left over: `search_filter.rs` is down to Tempo's `tags`-parameter-to-`Condition` parser (an HTTP encoding, not a lowering — design D4); `logql.rs`/`logql_metric.rs` keep a real (if now secondary) DataFusion lowering for the LogQL constructs `ql_ir` still refuses as `Inexpressible` (`quantile_over_time` and a handful of others — `design.md`'s fallback-set writeup has the current, enumerated list) and the response-assembly code every LogQL request goes through regardless of which lowering produced its rows. PromQL is untouched by this and still has no crate of ours (the third-party `promql-parser` supplies the grammar) or IR path — `querier/query/promql.rs` remains PromQL's sole, primary lowering. TraceQL's rejection class decides the HTTP status: unparseable → 400, valid-but-unimplemented → 501:
   - `/loki` (LogQL, epic #366): `LogsService` executes log queries (streams) and metric queries (`rate`/`count_over_time`/`sum by`, `date_bin` bucketed matrix); `LogsService` also backs `/loki` labels/values/series and `detected_fields` (sampled attribute-field discovery: name, inferred type, approx cardinality — epic #737 L3). `batches_to_streams` keeps only `service_name`/`level` as stream labels and emits trace context plus log+resource attributes as per-entry **structured metadata** (`common::attrs::attr_documents` decodes both the legacy JSON-string and typed `Map<Utf8,Utf8>` storage forms). Loki's metadata is a flat string map, so the three OTel attribute scopes are flattened here and scope attributes are absent — a wire-format limit, not a storage one.
   - `/prometheus` (PromQL, epic #328): `MetricsService` executes selectors, `sum/avg/min/max/count [by]`, and `rate`/`increase` over `metrics_gauge`+`metrics_sum` (`date_bin` bucketed matrix), plus `histogram_quantile(phi, metric)` interpolated from `metrics_histogram` OTLP buckets; `MetricsService` also backs `/prometheus` labels/values/series. The router serves a `/prometheus/api/v1/label_stats` extension (per-label cardinality) directly from the catalog's `attribute_stats`, without a Querier round-trip. `histogram_quantile` over an inner `rate()`, binary ops, and `topk` remain pending (#335).
   - `/pyroscope` (profiles) via `ProfileService`.
   - `POST /api/v1/query` (native **Query IR**, epic query-ir-core): the first-party structured query surface (versioned JSON IR over `logs`/`traces`/profile-summary `profiles`/scalar `metrics`/bucketed `metrics_histogram`, not a dialect string). `endpoints/query.rs` selects the source's read scope (`metrics_histogram` maps to the same `metrics:read` scope as `metrics`) before it stamps the server clock and forwards a `query_ir:{tenant}:{dataset}:{json}` ticket to the querier's `IrService`, which validates + lowers the IR to a DataFusion `DataFrame` (promotion-invariant field resolution, three-valued absent semantics) and returns `rows`/`series`/`table` envelopes. Profile rows expose only registered scalar metadata (`profile.id`, timestamps/duration, sample/period metadata, service and trace/span IDs) plus logical profile/scope/resource attributes; `samples_json`/`stacktraces_json` and raw attribute payloads stay unaddressable as fields on any envelope, including `flamegraph` below — that envelope retrieves the aggregated payload, never the raw JSON. `metrics` unions `metrics_gauge`+`metrics_sum` (one scalar `metric.value` per row, `timestamp`/`metric.name`/`service.name` plus resource attributes; every scalar source registers its primary time column as a logical field — `timestamp` on logs/metrics/metrics_histogram/profiles, `start_time_unix_nano` on traces — so `max(timestamp)` works uniformly, #1205) — `SourcePlan` scans a list of physical tables per source (`tables`, not a single `table`) and unions them onto `row_defaults` when there's more than one, which is what lets a source span multiple physical tables at all; each table's scan is wrapped in a `CoercedTableProvider` that presents exactly `row_defaults` — same columns, same order, coerced types (JSON→Map via the `ir_json_to_map` UDF, or a cast) — _before_ the union. A provider rather than a projection expression because DataFusion 54's `optimize_projections` mis-orders pushed-down projections under a UNION whose inputs mix columns and expressions (#1206); presenting the whole shape rather than only reconciling types because the tables also disagree on column order and count (`metrics_sum` carries two extra mid-schema columns), and `optimize_projections` rebuilds each branch's scan projection from sorted indices — so any node pushed between projection and scan, such as a predicate pushed below the UNION, rebuilt the branches against different index spaces and failed the plan with "UNION field 0 have different type in inputs" (#1348). Identical scan schemas leave nothing to misalign. The same `CoercedTableProvider`/`ir_json_to_map` machinery also covers a _single_-table source (`coerce_legacy_containers`, called from `scan_source_tables`'s one-table branch): a table written before the Map-typed-attribute migration stores an attribute container as a flat JSON string, which `get_field` cannot read — a hard execution error, not a graceful IR rejection, for an otherwise-valid document. There the provider presents the table's own full column list (not `row_defaults` — a single-table source keeps its full raw schema, which `SchemaResolver`'s promoted-attribute discovery depends on), coercing only the legacy containers it finds to a canonical `Map<Utf8,Utf8>`. `metrics_histogram` (IR v3+) is a separate single-table source (one whole bucketed histogram — `bucket_counts`/`explicit_bounds` — per row, not a scalar) reachable only through the terminal `histogram_quantile` stage, which — because merging bucket-array columns element-wise isn't expressible as a DataFusion aggregate — is the one stage that breaks the otherwise-lazy `DataFrame` chain: it `.collect()`s the filtered/bucketed rows, reuses the exact bucket-merge/interpolation functions the PromQL `histogram_quantile()` path calls (`querier::query::histogram`, shared so both surfaces return identical percentiles), and reinjects the small aggregated result as a fresh in-memory DataFrame shaped like `aggregate`'s `step` output so every downstream stage and the response builder need no histogram-specific handling. IR v5 adds `stddev`/`stdvar`/`first`/`last` aggregates and an aggregate `divisor` (value ÷ scalar, which is what a rate is — the compat path already plans `rate` as `Count` + `rate_divisor_seconds`), so per-unit rates are now expressible; `irate`/`histogram_fraction` and cross-series formulas (`a / b`, `label_replace`) still have no IR equivalent, as they need computation across series rather than within one aggregate. Pyroscope endpoints retain diff, label discovery, extraction, and heatmap work. IR also has a `flamegraph` envelope, legal only for the `profiles` source: a `where`-only pipeline (no `aggregate`/`topk`/`order`/`extract` — the flamegraph aggregation is itself the terminal computation, not DataFusion-lowered) resolves matched rows through the same scanned/windowed/filtered `DataFrame` every other envelope uses, decodes the full rows (this is the one path that does read `samples_json`/`stacktraces_json`, server-side only), and calls the same `aggregate_profiles_to_flamegraph` the Pyroscope render path uses — capped at `FLAMEGRAPH_PROFILE_CAP` (1,000) profiles with an exact `truncated` flag via `df.limit(cap+1)`. The result crosses the Flight wire as a single-row RecordBatch (`flamegraph_json`, `truncated`) the router decodes into the response's `flamegraph` field. The MCP `get_profile` tool wraps this path for single-ID lookup, rendering an interactive flamegraph via MCP Apps for capable clients (see `mcp-tool-surface`/`docs/users/mcp.md`). IR v2 additionally has a terminal `heatmap` relation for sparse, epoch-aligned time-by-numeric distributions; trace duration heatmaps retain the precise span-start predicate and timestamp partition-pruning bounds. No trace-specific HTTP endpoint or Flight ticket exists. `endpoints/query.rs` encodes attribute containers as JSON objects (`map<string,string>`); `canonical_arrow_type` returns `Option` so "no canonical form" is distinct from "cast failed". This is the only surface that keeps OTel's three attribute scopes distinct: `SourcePlan` lists `log`/`span`/`profile`, `scope` and `resource` containers, a field may carry a container qualifier (`resource.`/`scope.`/`log.`/`span.`/`profile.`) to read exactly one where a bare name coalesces, and the logs `rows` default projects the whole LogRecord (trace context incl. `trace_flags`, `severity_number`, scope identity, schema URLs, all three containers unmerged). On `traces`, `exception.type`/`.message`/`.stacktrace`/`.escaped` resolve specially to a new `Resolved::EventAttribute` variant rather than a span attribute: a dedicated `ir_event_attr` DataFusion UDF (`ir_planner.rs`) parses the span's stored `events` JSON array (`common::model::span::parse_span_events`), finds the first event named `exception`, and extracts the key from its own attributes — a span with no such event resolves the field absent even when `status.code = Error`. Logs need no equivalent: per exceptions-on-logs semconv, the same four names are ordinary LogRecord attributes there, resolved by the normal attribute-container fallback. Physical addressing stays rejected through the resolver's `is_physical_name` check (the static `STORAGE_DENYLIST` was replaced by the logical schema's physical-name set), and retrieval-only fields such as the log `body` are rejected in predicates, grouping, and ordering — the widened defaults are server-chosen, not client-nameable. Client-visible built-ins (record metadata, join keys, standard resource/scope attributes) are declared in `LogicalSchema::core()` (`src/common/src/schema/logical.rs`), independent of the physical Iceberg layout. Result columns are aliased through `common::query_ir::safe_ident` (shared with the router, which reads them back out of the batches) and referenced as literal identifiers, never `col()`, which lowercases an unquoted SQL identifier and used to 500 a mixed-case group key (#1070). Any envelope may carry `warnings[]` (stable `code` + message + suggestions): `unknown_group_by_field` is raised in the router when an `aggregate.by` field is neither a logical field of the source nor non-null on any row of a non-empty result — a warning, not a rejection, because unpromoted attributes aren't enumerable at plan time until the attribute registry (#813) lands. The UI (Explore "Query" tab) and CLI (`query --ir`) consume it via generated clients. See `tempo-api` skill and `docs/users/querying-ir.md`.
7. Semantics of attribute keys / entity types / metric names come from the schema registry (change `schema-registry`): the vendored OTel semconv (`vendor/otel-semconv/`) and `otel/registry/` are parsed by the `schema-model` crate (parser + resolver + validator, no FDAP deps) into bundled read-only registries; tenant custom registries in the same Weaver model are stored in the catalog; the router serves list/CRUD/validate and attribute/entity/metric resolution under `/api/v1/schema/*` (`endpoints/schema.rs`, `schema:read`/`schema:write` scopes); the SDK exposes it as `schema_*` methods, the CLI as `schema <noun> get|search` / `admin schema create|replace|delete|validate --file` (YAML or JSON), and the MCP server as `list_schema_registries`, `resolve_attribute|entity|metric`, `search_schema`, and `create|replace|delete_schema_registry`.
8. Router serves the explore UI (static SPA from `src/ui`) at the **root** (SPA fallback behind the API routes) from the directory named by `SIGNALDB_UI_DIR` (`src/router/src/ui.rs`); unset -> placeholder page, set-but-invalid -> startup failure. Container images ship the assets preinstalled. Browser auth: `POST/DELETE /ui/session` (`src/router/src/endpoints/session.rs`) sets/clears an HttpOnly `signaldb_session` cookie the auth middleware accepts in place of auth headers; login tenant is optional (response lists memberships; sole membership auto-selected, several → UI tenant picker) and each request re-validates `X-Tenant-ID` against memberships; `GET /api/v1/whoami` returns the authenticated tenant + datasets.
9. Router is also the **OAuth 2.1 authorization server** for MCP connectors (change: mcp-oauth-dcr), off unless `[mcp.oauth]` is enabled: discovery, DCR, `/oauth/authorize` + a React consent screen at `/oauth/consent`, and `/oauth/token`. Claude.ai/ChatGPT register with no headers; the opaque, audience-bound access token carries its own tenant + read scopes. See the `multi-tenancy` skill and `docs/users/mcp.md`.

## Deployment Models

- **Monolithic** (`cargo run --bin signaldb`): All services in one process, shared SQLite catalog. Compactor included (enabled by default; opt out with `[compactor].enabled = false`).
- **Microservices** (`signaldb <service>`): the same `signaldb` binary runs one service per process — `acceptor|router|writer|querier|compactor|mcp` are clap subcommands of `signaldb-bin`'s `Cli` (shared `--config/-v/-q` are global), each backed by that crate's `cli::Args` + `cli::run(common, args)`; there are no per-service `[[bin]]`s. Shared catalog (PostgreSQL or SQLite). Images ship the one binary with `signaldb <service>` as entrypoint (openspec `multi-call-binary`).
- **Hybrid**: Mix of co-located and distributed services

**Note**: Monolithic mode runs the same compactor lifecycle loop as the standalone service (`compactor::service::CompactorService`) when `[compactor].enabled = true` (the default; retention enforcement — 30d for each of traces, logs, metrics and profiles — and orphan cleanup are also both on by default), and serves the compactor Flight endpoint (50055) plus observability HTTP on `[compactor].metrics_addr`. The lifecycle loop covers:

- Compaction planning and execution (Parquet rewrite for storage efficiency), scoped to one closed `timestamp_hour` partition per job and committed as an Iceberg delta (remove inputs / add outputs) so cost tracks the partition rather than the table and concurrent ingest does not invalidate the commit. The rewrite **streams** the partition in two passes — an unsorted scan that folds the attribute statistics, then the sorted scan that feeds the writer — so peak job memory is the DataFusion pool (`[compactor] memory_limit_mb`, spilling past it) plus one output file, not the partition (#1064). The scan feeds that sort in `[compactor] scan_batch_size`-row batches, since the sort's per-batch reservation is unspillable and scales with row width. The service warns at startup when `memory_limit_mb`, `target_file_size_mb`, `target_partitions` and `sort_spill_reservation_mb` are combined in a way that cannot work — a target at or above the pool, a per-sorter share too small for a spilling sort, or headroom claiming half that share
- Retry classification per failed job attempt (`compactor::executor`, #1052): commit conflicts and transient infrastructure failures (typed `object_store`/`io` errors plus a marker list for the stringly-typed catalog and iceberg-fork errors) share one exponential-backoff budget; anything not positively identified as transient is terminal and fails on the first attempt instead of repeating the rewrite. The class is exported as the `error_type` label on `compactor_jobs_failed_total`, alongside the tenant/dataset/table labels the job counters carry — declared as `type: metric` groups in `otel/registry/signaldb.yaml` and pinned to the exporter by `src/compactor/tests/registry_pins.rs`
- Retention enforcement, snapshot expiration, and orphan file cleanup. Orphan liveness comes from the union of the retained snapshots' manifests (never snapshot age), and a re-validation pass rebuilds that set before every real deletion batch, unconditionally. That set is built with bounded memory (#475): manifests are deduplicated across snapshots so each is read once, entries stream past a visitor, the set keeps a 64-bit fingerprint per live path instead of the path, and the object-store listing is streamed — a fingerprint collision keeps an orphan, it can never hide a live file. Per-file deletion lines are `DEBUG` (a backlog pass deletes tens of thousands of files at boot); batch/run summaries are `INFO`
- Distributed-lease expiry (every 30s) for multi-instance safety

Planning is stateless — candidates are re-derived from file count and size each tick — so the cross-cycle memory lives in `RoundRobinScheduler` (`compactor::scheduler`): a failure cooldown that suppresses a partition for 15 minutes, doubling per consecutive failure to a 6-hour ceiling, cleared outright by a success (#1053). Without it a partition that cannot commit stays eligible forever and is retried every `tick_interval` indefinitely. Suppressed candidates are filtered before the per-tenant cap, so they cannot occupy a slot they are then skipped from, and the key is `(tenant, dataset, table, partition)` because `partition_id` alone is an hours-since-epoch bucket shared across tables. `CompactionStatus::Conflict` deliberately does not arm the cooldown — a conflict is CAS contention to retry, not a stuck partition — so cooldown wiring must not be collapsed with the retry classification in `commit.rs`/`executor.rs`.

The attribute-stats pass (per-key presence/cardinality + advisory materialization candidates, epic #737 L4a) is the rewrite's first streaming pass; it plans no sort, since presence and cardinality are order-independent. Compaction, retention enforcement, orphan cleanup and lease expiry each run on their **own** task at their own cadence (`compactor::lifecycle`), so a long compaction cycle no longer delays the others (#1011); three of the four then take turns per table — a `TableLockRegistry` (`compactor::table_lock`) hands out one async mutex per `(tenant, dataset, table)`, taken by compaction commits, retention partition drops and snapshot expiration, so those never act on one table at once while different tables never contend. Lease expiry and orphan cleanup's deletion pass do not take it (the former touches no table metadata; the latter is guarded by its live-set check plus unconditional pre-delete re-validation). Every cycle iteration is also guarded with `catch_unwind` (caught, counted in `CycleHealth`, retried with backoff) so a bug in one cycle can't end that task permanently either — `compactor_cycle_panics_total`/`compactor_cycle_down` surface it, while `/health` stays a pure liveness probe (always `200`) so a recovering cycle never trips a container restart. `catch_unwind` needs an unwinding panic strategy; this workspace's `[profile.release]` sets `panic = "abort"`, so the guard isn't load-bearing in a release build today. The admin `compact_now` action runs `execute_candidate` on its own Flight request task, but that is the same method the background cycle calls on the same shared `Arc<CompactionExecutor>`, so acquiring the table lock inside it covers both entry points; retention acquires the same lock across drop-plus-expire, covering both the retention cycle and orphan cleanup's pre-expire call. That serialization is in-process only — cross-process safety rests on catalog CAS plus the compaction commit's input-scoped validation. Every rewrite also runs the advisory attribute-stats pass (persisted to the catalog's `attribute_stats` table; dry-run promotion decisions under `[compactor.attr_promotion]` — epic #737 Layer 4).

## Dual Catalog System

1. **Service Catalog** (`Catalog`): PostgreSQL/SQLite for service discovery, tenant management, API keys (each carrying explicit scopes from `common::auth::API_KEY_SCOPES` — ingest `*:write`, read `*:read`, `schema:read`/`schema:write`, and the explicit-only `tenant:manage` that lets a key call the tenant management API for its own tenant (`TenantContext::can_manage_via_key`; legacy unscoped keys never gain it) — plus an optional dataset restriction, editable via `PATCH .../api-keys/{key_id}`), datasets. Monolith startup syncs config tenants into it; on a truly-empty first boot (no tenants in config or catalog) it auto-provisions a `default` tenant and prints the generated API key once (`common::bootstrap::bootstrap_default_tenant`). Router and monolith boot also run `Catalog::backfill_default_datasets`, materializing a `datasets` row for any tenant naming a `default_dataset` without one — tenant creation no longer produces that state, but older deployments carry it and it fails auth closed (#1066)
2. **Iceberg Catalog** (`CatalogManager`): SQLite-only SQL catalog named `"signaldb"` for Iceberg table metadata

The Iceberg catalog only supports SQLite (not PostgreSQL). This is distinct from the service catalog.
