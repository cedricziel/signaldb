## Context

See `proposal.md` — Why. Current state that shapes the approach:

- `signaldb-sdk` is generated by `cargo xtask generate` (progenitor) from the
  code-first OpenAPI surface. Today it is a single `generated.rs` plus a
  re-exporting `lib.rs` — HTTP-only, no hand-written code.
- **How queries actually reach the server today** (verified in code, and it is
  _not_ a single uniform Flight surface):
  - **SQL** is the only query reachable as a raw external Flight ticket: the CLI
    sends the SQL string to the router's Flight endpoint (`:50053`);
    `execute_query` returns `NotFound` for it, and `do_get` falls through to
    `proxy_to_querier`, which runs it on the querier.
  - **PromQL / LogQL / TraceQL** have **no external Flight entrypoint that
    accepts a raw query string.** They are accepted only over the router's HTTP
    compat endpoints (`/prometheus/...`, `/loki/...`, `/tempo|api/...`), where
    the router parses the string, builds an _internal_ querier ticket
    (`query_promql:{tenant}:{dataset}:{json}`, `query_logs:…`), and converts the
    querier's batches into native Tempo/Loki/Prometheus JSON. The querier's
    ticket vocabulary is an internal router→querier protocol, not a public API.
- The CLI's `commands/query.rs` and `tui/client/flight.rs` construct their own
  `FlightServiceClient` — the two rule-violating sites this change removes.
- `mcp-server` already depends only on `signaldb-sdk` and calls
  `signaldb_sdk::Client` — the proven pattern the CLI must follow.
- The router's Flight `do_action` is unimplemented. The compactor already
  exposes a Flight `do_action` control surface plus read-only HTTP `/status`
  and `/health` on its own port; it is the backend the ops proxy forwards to.

FDAP constraint: the SDK's SQL query module handles Arrow `RecordBatch`es and
MUST use the Arrow types re-exported through DataFusion/`arrow-flight` already in
the workspace, to stay version-aligned with the server. The router Flight
endpoint returns the **v1 wire** schema; the SDK surfaces those rows as-is — no
v2 storage schema is involved and nothing changes on the wire. The compat
endpoints' JSON responses are passed through unchanged.

## Goals / Non-Goals

**Goals:**

- Make four-way parity (API ≡ SDK ≡ CLI ≡ MCP) structural, enforced by a test.
- Give the SDK full query coverage matching the server's real transports: SQL
  over Flight, the three native languages over the HTTP compat endpoints.
- Keep the SDK maximally generated; hand-write only what OpenAPI cannot express.
- Ship in reviewable phases with a clean dependency order.

**Non-Goals:**

- Ingest/write from CLI or MCP (excluded in the proposal).
- Changing query _semantics_ or the native JSON response shapes.
- A uniform cross-language row model, or a `--compat` flag (both dropped — see
  D2).
- Adding a new external Flight surface for PromQL/LogQL/TraceQL (rejected in D2).
- Code-generating CLI verbs or MCP tools (rejected in D4).

## Decisions

### D1 — SDK covers query with two transports matching the server

The SDK exposes four query methods aligned to how the server is built:

- `query_sql` → router **Flight** (`:50053`), returning Arrow rows. Hand-written,
  because OpenAPI cannot describe the gRPC/Arrow-Flight transport.
- `query_promql` / `query_logql` / `query_traceql` → the router's **HTTP compat
  endpoints**, returning the native Tempo/Loki/Prometheus JSON. Reached through
  the **generated** client (see D3-bis) — no hand-written HTTP.

`lib.rs` unifies the generated client and the one hand-written Flight module
under a single `Client`.

- **Alternatives:** (a) hand-write HTTP for the three native languages in the SDK
  — rejected: violates "SDK consumes only generated clients / no hand-written
  HTTP." (b) A second SDK crate for Flight — rejected: splits the "one client"
  contract the parity rule depends on.

### D2 — Native per-language output; no uniform model, no `--compat`

Query results are emitted in each language's native shape: SQL yields tabular
rows (`table`/`csv`/`ndjson`); PromQL/LogQL/TraceQL yield their native
Tempo/Loki/Prometheus JSON, passed through untouched. There is no cross-language
row normalization and no `--compat` flag.

- **Why the earlier "uniform rows" decision was reversed:** it assumed a single
  Flight surface accepting raw strings for all four languages (see Context) —
  which does not exist. Only SQL has a Flight path; the other three are
  HTTP-compat-only and already return native JSON. Normalizing them to rows would
  mean re-parsing Grafana JSON into a row model in the SDK for no user benefit.
- **Alternative — grow per-language Flight entrypoints on the router so a uniform
  model becomes possible** — rejected: real server work duplicating the existing
  HTTP query surface, for output uniformity the user explicitly does not want.

### D3 — Ops reachable only via the router proxy (direct-to-compactor forbidden)

Because CLI/MCP may use only the SDK, and the SDK's HTTP client reaches only the
router, operational control MUST be a router endpoint. The router grows an
OpenAPI-annotated `/api/v1/ops/*` proxy that forwards to the compactor's Flight
`do_action`. Being annotated, it regenerates into the SDK for free.

- **Alternative:** CLI talks to the compactor's Flight directly — rejected:
  violates the SDK-only rule and hard-wires a second endpoint into every
  consumer.

### D3-bis — Annotate the existing compat query endpoints into OpenAPI

The PromQL/LogQL/TraceQL compat endpoints exist but are not in the code-first
OpenAPI surface, so they do not generate into the SDK. This change annotates
them (request params + a response schema; a loose/`serde_json::Value`-style
response is acceptable since the native JSON is passed through) so the generated
SDK gains `query_promql`/`query_logql`/`query_traceql`. No behavior or response
shape changes — annotation only.

- **Alternative:** hand-write these three HTTP calls in the SDK — rejected: same
  "no hand-written HTTP" reason as D1(a).

### D4 — Parity enforced by a manifest test, not codegen

A `tests-integration` check enumerates the SDK's public capability surface and
asserts each has a CLI verb/flag and an MCP tool. The SDK-only rule already
prevents consumers from _exceeding_ the SDK; this test catches _under_-exposure.

- **Alternative:** generate CLI verbs and MCP tools from the SDK — rejected:
  high upfront cost and it fights the hand-written Flight portion, which has no
  OpenAPI to generate from.

### D5 — One `query` command, language as a mutually-exclusive flag

Queries are a single `query` command with exactly one required language flag:
`signaldb query --sql|--promql|--logql|--traceql '<q>'`. The language fully
determines the signal (promql→metrics, logql→logs, traceql→traces; sql is
cross-signal), the transport (sql→Flight, others→HTTP compat), and the output
shape. Management is `admin <noun> <verb>`; operational control is `ops <verb>`.
This moves today's top-level `tenant`/`api-key`/`dataset` under `admin` and
changes query invocation — a **breaking** CLI-surface change (see Migration).

- **Alternatives:** `query <lang>` subcommands or signal-first
  (`metrics query --promql`) — rejected: the flag form is flattest, the language
  already implies the signal, and `--sql` stays a peer flag rather than a
  homeless noun.

## Risks / Trade-offs

- **Two SDK code paths (generated HTTP + one hand-written Flight module) confuse
  contributors** → `lib.rs` documents the boundary; the Flight module lives in
  its own file and the generated header already says "Do not edit."
- **Ops proxy is a Phase-2 server dependency; CLI `ops` verbs can't land before
  it** → phasing makes this explicit; Phases 0–1 (query + admin parity) deliver
  value without it.
- **Loose OpenAPI response schema for the compat endpoints yields a weakly-typed
  SDK return (opaque JSON)** → acceptable: the CLI/MCP pass the native JSON
  through; a tighter schema can be layered later without changing behavior.
- **Arrow/DataFusion version drift between SDK and server (SQL path)** → SDK uses
  only the workspace-pinned `arrow-flight`/DataFusion re-exports; covered by the
  FDAP alignment rule and an integration test against a live router.
- **Parity test asserts presence, not behavioral equivalence** → complement with
  a cross-surface result-equivalence test (same query via CLI and MCP yields
  equivalent data in that language's native shape), per `mcp-tool-surface`.
- **Breaking CLI reorg affects scripts and docs** → see Migration. Post-1.0, no
  back-compat aliases are added; the break is announced, not shimmed.

## Migration Plan

Phased, each phase independently shippable as a small PR (or stack):

- **Phase 0 — SDK query keystone:**
  - Annotate the PromQL/LogQL/TraceQL compat endpoints into OpenAPI and
    regenerate the SDK (D3-bis) — gains `query_promql`/`query_logql`/
    `query_traceql`.
  - Add the hand-written Flight `query_sql` module to `signaldb-sdk` (D1).
  - Unblocks CLI and MCP query.
- **Phase 1 — CLI + MCP query parity:** CLI drops `FlightServiceClient` in
  `commands/query.rs` and `tui/client/flight.rs`, routes all four query flags
  through the SDK, and re-taxonomizes commands (`query --<lang>`, `admin`
  grouping). MCP adds query tools. Land the parity test (D4) covering query +
  admin.
- **Phase 2 — Ops:** router `/api/v1/ops/*` proxy (server) → regenerate SDK →
  CLI `ops` verbs + MCP ops tool; extend the parity test to ops.

**CLI breaking-change handling:** the reorg moves top-level `tenant`/`api-key`/
`dataset` under `admin` and changes query to `query --<lang>`. Announce in the
CLI changelog and update `docs/architecture/overview.md`, `docs/users/
authentication.md`, and the `multi-tenancy` skill's CLI examples in the same PR.
No back-compat aliases (post-1.0).

**Rollback:** each phase is independently revertible. Phase 0 and Phase 2 are
additive (the Phase-0 SDK additions are inert unless called; reverting Phase 2
removes the ops surface without touching query/admin). Phase 1 is the one
**breaking** step — it reshapes the CLI command tree — so its rollback is a
coordinated CLI release rollback that restores the prior command tree, not a
silent additive revert.
