## 5. Executor/rewriter: bounded streaming rewrite (D4, #933)

- [x] 5.1 (#1020 added `oversized_partition_stays_within_its_memory_budget`: a 1 MB budget against a 10k-row partition must complete with rows preserved, or fail with an attributable error leaving the live set untouched — never OOM. Note it currently resolves via the success branch, so it pins the no-OOM/no-corruption contract rather than proving a spill occurred.) Tests: rewrite of one partition leaves other partitions' files byte-identical; peak-memory test with a small `FairSpillPool` budget completes or fails attributably (no OOM); row-count parity preserved
- [x] 5.2 (#1017 scoped the read to one partition with a pushed-down predicate; #1064's stack replaced `collect` with `execute_stream`) Scope `rewrite_table` → `rewrite_partition(inputs)`: register only input files, `execute_stream` instead of `collect`, per-partition sort retained
  - **Design note:** streaming forced the rewrite into **two passes**, not one. The promotion decision must be settled before the first output batch is written, but it is made from statistics gathered by scanning the same data — a constraint `collect()` hid by keeping everything resident. Pass 1 is an _unsorted_ scan that folds the statistics (order is irrelevant to presence and cardinality, so it plans no sort and stays cheap); pass 2 is the sorted scan that feeds the writer.
  - Deciding promotion from the previous cycle's persisted stats would have saved the second scan, but the partition that first reveals a hot key would then never materialize it — and a compacted partition is not compacted again, so those files would never gain the column. Rejected on that basis; the existing promotion/demotion integration tests pass unchanged, which is the evidence the semantics held.
- [x] 5.3 **reopened (#1064), closed again (#1067 + #1068)** Build compaction `RuntimeEnv` with `FairSpillPool(compactor.memory_limit_mb)` + spill config (new config keys)
  - **Correction:** #1017 marked this done via `RuntimeEnvBuilder::with_memory_limit` (the querier's idiom), but that installs a **`GreedyMemoryPool`**, not a `FairSpillPool` — the spec's own requirement was never met. Live on hive the pool reports `greedy(used: 511.9 MB, pool_size: 512.0 MB)` and the rewrite fails in `read_and_merge` before any commit is attempted, every cycle.
  - Split into two steps: bound the fan-out so the budget is not divided by core count (`compactor.target_partitions`, this PR), then swap the pool shape for `FairSpillPool` behind a helper shared with the querier (#941).
  - Note the failing consumers are not all spillable: hive logs show `ExternalSorterMerge`/`SortPreservingMergeExec` reservations of 50–103 MB with `can spill: false`, which `FairSpillPool` fair-shares _around_ rather than bounding. Bounding the fan-out is what caps how many of those exist.
  - **Resolution:** both steps landed. #1067 added `compactor.target_partitions` (default `1`) and pins it on the rewrite's `SessionConfig`, so the pool is no longer divided by core count. #1068 moved pool construction into `common::datafusion_runtime::bounded_memory_pool` — a `FairSpillPool` wrapped in `TrackConsumersPool` — shared by the compactor's `compaction_context()` and the querier's runtime, which is what closes #941's drift risk. Spill needs no key of its own: `RuntimeEnvBuilder`'s default `DiskManager` already spills to the OS temp dir, so `target_partitions` is the new key the task called for. `warn_on_incoherent_memory_config` (#1081) surfaces settings that cannot work together, and `docs/operations/compactor/configuration.md` carries the sizing model.
- [x] 5.4 Roll output files at target _encoded_ size using writer bytes-written feedback; test that merged output approximates target file size
  - The pinned fork already rolls on real encoded bytes (`bytes_written() + in_progress_size()`, upstream JanKaul/iceberg-rust#388) — but only against the table property `write.target-file-size-bytes`, which SignalDB never set. Every table therefore rolled at the writer's 512 MiB fallback, so `target_file_size_mb` was inert and a partition became exactly one output file. `common::iceberg::table_manager::ensure_target_file_size_property` now reconciles the property from the compaction path immediately before each rewrite (metadata-only, no-op once matching, logged-not-fatal on a lost CAS race). Reconciling per rewrite rather than setting it at creation is deliberate: a planner selecting files under `target_file_size_mb` while the writer rolls at a stale value never converges.
  - **Second defect, found only because the test stayed red after the property fix:** the writer rolls only _between_ the batches it is handed, never inside one — and DataFusion returns a small partition's whole scan as a single `RecordBatch`, so the chunker handed the writer exactly one unit and no roll could occur. `rewrite_stream` now splits an oversized batch into target-sized row windows.
  - **Third defect, in the split itself:** `RecordBatch::slice` shares the parent's buffers, so `get_array_memory_size()` on a slice reports the _parent's_ full capacity (`arrow-data`'s `get_slice_memory_size` is the prorating one). Charging that per slice forced a flush after the first slice every time. Fixed to charge `take_rows * bytes_per_row`, with the exact measured size kept for unsliced batches — `bytes_per_row` truncates, and re-deriving a whole batch from it undercounts cumulatively. Slicing is now applied only to batches that are themselves oversized: `bytes_per_row` embeds fixed per-batch overhead, so slicing every batch to top up to exactly the target cut small batches in two over that inconsistency and stranded tiny remainder chunks.
  - Tests: `tests-integration/tests/compactor/target_encoded_file_size.rs` (red→green across all three defects) plus unit tests pinning both directions — `chunking_splits_a_single_oversized_incoming_batch` and `chunking_coalesces_an_oversized_batchs_tail_with_following_small_batches`. The coalescing test is the one that exposed defect three; the splitting test passes under it.

## 6. Commit: delta semantics + typed conflicts (D2, part of #933)

- [x] 6.1 (#1020 added `delta_commit_aborts_when_its_inputs_are_no_longer_live`: an input file removed underneath the job — the shape a concurrent partition drop leaves — aborts the commit, classifies as a conflict, and creates no snapshot, so any already-written output stays unreferenced and reclaimable) Tests: commit succeeds while ingest appends concurrently to another partition (no retry starvation); retention dropping the target partition aborts the commit; failed commit leaves output files unreferenced (reclaimable)
- [x] 6.2 (#1017) Replace whole-table `replace` with the scoped delta commit; conflict check = input files still live in target partition at commit time
- [x] 6.3 (typed `CommitError::SnapshotConflict` predates this change; `commit_delta` raises it for a mutated input set and keeps post-commit verification) Replace substring conflict classification with typed errors (also fixes the self-authored verification errors); keep post-commit catalog verification
- [x] 6.4 Per-table async mutex serializing compaction/retention/expiration loops in-process (D6)
  - **Still required — an earlier note here claimed otherwise and was wrong.** It is true that `run_lifecycle_loop` serializes its _own_ cycles: it is one spawned task whose `tokio::select!` arms each `.await` to completion, one loop per process. But that is not the whole picture. `CompactorFlightService::do_action("compact_now")` calls `executor.execute_candidate(...)` directly on the Flight request task (`compactor/src/flight.rs:193-208`), entirely outside that loop — so an admin-triggered compaction _can_ run concurrently with a retention or snapshot-expiration cycle on the same table. Leases cover compaction-vs-compaction only; retention and expiration take none.
  - Scope for the fix: a shared per-table async mutex (or equivalent conflict-and-retry guarantee) covering compaction from both entry points, retention drops, and snapshot expiration — which additionally commits without conflict retry today. #1011 widens the exposure by splitting the cycles into independent tasks, but it is not a prerequisite.
  - **Implemented:** `TableLockRegistry` (`src/compactor/src/table_lock.rs`) — a `DashMap` of one `tokio::sync::Mutex<()>` per `(tenant, dataset, table)`, created once in `CompactorService::new` and shared with both `CompactionExecutor` and `RetentionEnforcer`. The guard is taken inside `CompactionExecutor::execute_candidate`, which is the single method _both_ compaction entry points call on the same shared `Arc`, so the Flight `compact_now` path is covered without touching `flight.rs`; and inside `RetentionEnforcer::enforce_table_retention`, which covers partition drops and snapshot expiration together (`expire_old_snapshots` is called from within it) for both the retention cycle and orphan cleanup's pre-expire call. Different tables never contend. The lease mechanism (cross-process, compaction-vs-compaction) and the coarser `RetentionCycle.gate` are left in place — neither is subsumed.
  - **Known bound, deliberately not mitigated here:** the guard is held across the whole retry loop. Backoff is hard-bounded (300 ms under `ExecutorConfig::default()`), but per-attempt rewrite time is only memory-bounded (D4), not time-bounded, and a conflict redoes the whole rewrite — so worst case a same-table retention pass waits up to 3 full rewrite attempts. Releasing between attempts was considered and rejected: it would let retention slip in mid-retry and _cause_ the next conflict, defeating part of D6's purpose. A job-level deadline independent of retry count is the better fix if the wait ever proves painful; filed as a follow-up rather than scope-crept here.
  - Test: `retention::enforcer::tests::compaction_and_retention_do_not_interleave_on_the_same_table`, driving the real `execute_candidate` / `enforce_retention` entry points in both directions. A first version asserted liveness with wall-clock deadlines and proved flaky under build load; it now asserts via `JoinHandle::is_finished()` plus an explicit start rendezvous, with timeouts kept only as deadlock backstops. Verified 18/18 clean, 8 of those runs against a concurrent `cargo build --workspace -j 8`. Confirmed load-bearing by removing the compaction-side guard and observing the expected failure.
