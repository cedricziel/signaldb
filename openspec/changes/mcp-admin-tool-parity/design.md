## Context

See proposal.md — Why. Current state:

- SDK operations (progenitor, from `api/signaldb-api.json`): admin family (`list_tenants`, `create_tenant`, `get_tenant`, `update_tenant`, `delete_tenant`, `create_user`, `list_api_keys`, `create_api_key`, `revoke_api_key`, `update_api_key`, `list_datasets`, `create_dataset`, `delete_dataset`), management family (`manage_create_tenant`, `manage_list_datasets`, `manage_create_dataset`, `manage_delete_dataset`, `manage_list_api_keys`, `manage_create_api_key`, `manage_revoke_api_key`, `manage_update_api_key`, `manage_list_memberships`, `manage_upsert_membership`, `manage_remove_membership`, `manage_get_schema`), plus query, ops, schema-registry, `whoami`, OAuth consent.
- MCP wraps admin `create_api_key`/`list_api_keys`/`update_api_key` (+ ops, schema, query). CLI wraps the admin family and ops/schema/query; neither wraps `manage_*`.
- `src/router/src/endpoints/tenant.rs` (`/api/v1/tenants`, `/tenants/{id}`, `/tenants/{id}/tables`, `/tenants/{id}/tables/create`, `/tenants/{id}/schemas`, `/schemas/available`) has no utoipa annotations → not in the OpenAPI document → not in any client.
- Parity check: `tests-integration/tests/query_parity.rs` with hand-written `MANIFEST` (languages) and `OPS_MANIFEST` (compaction).
- Auth model since #1217: API keys carry scopes; humans carry membership roles; the router enforces both. No per-key role field; the MCP server does not filter `tools/list`.
- UI has management pages (API keys, instrumentation, tenant select) on the management API via the generated client; no tables view.

## Goals / Non-Goals

**Goals:** close #627/#628 under the current auth model; make the parity check exhaustive so this class of gap cannot recur; bring the tenant table/schema endpoints into the contract; UI/CLI/MCP/API parity for everything user-facing that this touches.

**Non-Goals:** role-based `tools/list` filtering (the router is the authority; not filtering matches the archived `mcp-server` spec); a `platform_health` tool (service discovery is not in the API/SDK today — file separately if wanted); the Pyroscope compat endpoints (not in OpenAPI; a separate parity item, noted for follow-up); retention status (no API today).

## Decisions

**D1 — Two MCP tool families by API, not by role.** Platform-admin tools keep the existing unprefixed names and wrap the _admin_ API (`create_api_key` etc. already do); tenant self-management tools are `tenant_*` and wrap the _management_ API. Rationale: the MCP server forwards the caller's credential; which family succeeds is decided by the router from that credential, exactly as for the CLI (`admin` vs new `tenant` group). Descriptions state which credential each family expects so an agent picks correctly. _Alternative:_ one tool per capability that picks admin-vs-management by probing `whoami` — rejected: hides which authority is acting, and the two APIs have different argument shapes (`tenant_id` vs implicit).

**D2 — Confirmation for destructive tools.** `confirm: String` must equal the target id (`dataset_id`, `tenant_id`, key id); mismatch → `invalid_params` naming what is required, no downstream call. rmcp `ToolAnnotations { destructive_hint: true, read_only_hint: false }` on those; `read_only_hint: true` on list/get/resolve/search/query tools. Annotations are asserted in a test over `tools/list`.

**D3 — Parity manifest derived from the SDK.** `signaldb-sdk` exports `pub const OPERATIONS: &[&str]` generated by xtask from the OpenAPI operation ids (same run that emits `generated.rs`). The parity test iterates it; a `const EXCLUDED: &[(&str, &str)]` (operation, reason) lists `oauth_consent_context`, `oauth_consent_decision` (browser consent flow), `whoami` (MCP: `server_info`; CLI: `whoami` exists or is added — decide by checking; if absent, add rather than exclude), and Flight SQL stays in the language manifest. CLI coverage is checked by parsing the clap command tree (`Command::debug_assert` + walk) against a `(operation → cli path)` map maintained next to the exclusion list; MCP coverage via `McpServer::has_tool` against `(operation → tool)` map. Both maps must be total over `OPERATIONS \ EXCLUDED`, and every excluded/mapped name must exist (stale entries fail).

**D4 — OpenAPI drift guard for routes.** A router test walks the axum route table (already possible via the OpenAPI golden test harness) and asserts every `/api/v1/**`, `/tempo/**`, `/loki/**`, `/prometheus/**` route (excluding an explicit allowlist: `/pyroscope/**` for now, session/login, static UI) has an OpenAPI operation. This is what makes "endpoint outside OpenAPI" a failing test rather than a code-review hope.

**D5 — tenant.rs joins OpenAPI.** Annotate the six handlers (`utoipa::path`, tag `tenants`), register in `openapi.rs`; regenerate. Response types already `Serialize` (`TenantApi` DTOs) — derive `ToSchema`.

**D6 — CLI `tenant` group** mirrors the MCP `tenant_*` tools 1:1: `tenant dataset {list,create,delete}`, `tenant api-key {list,create,update,revoke}`, `tenant membership {list,set,remove}`, `tenant schema get`, `tenant table {list,provision}`. Destructive verbs take `--yes` or prompt on a TTY, consistent with existing `admin` verbs.

**D7 — UI tables view.** Management area gets a "Tables" section per dataset (list from `listTenantTables`, button → `createTenantTables`), gated on the session's management right (same predicate as API-key management). Uses the generated client only.

## Risks / Trade-offs

- [Two tool families double the management tool count (~13 + ~13)] → clear naming and descriptions; agents already handle 25+ tools; `tools/list` stays unfiltered per the archived model.
- [Deriving the manifest from OpenAPI operation ids couples the parity test to id naming] → ids are stable (utoipa fn names) and the test names the exact missing id.
- [Route walk in D4 may need axum internals] → the OpenAPI golden test already builds the router; if the route table is not introspectable, keep a static route list asserted against `openapi.rs` and against `grep -r "route("` in CI.
