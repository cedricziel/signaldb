## Context

See proposal.md — Why. Builds on `query-throttle-signalling` (server emits `Retry-After`, `X-RateLimit-*`, JSON envelope with `retryAfterMs`).

Current state:

- **Rust SDK** (`src/signaldb-sdk`): progenitor 0.14 builder-style client generated by `cargo xtask generate` into `src/generated.rs`. The generated code holds a bare `reqwest::Client` and emits an empty `impl ClientHooks<()> for &Client {}`; progenitor's `ClientHooks::exec` is the single choke point every operation goes through, but progenitor offers no setting to supply a custom impl — only `with_inner_type` (a user type carried inside `Client`) and pre/post hooks (cannot retry). No `reqwest-middleware` in the workspace, and it would not help: progenitor calls `reqwest::Client::execute` directly.
- **CLI** builds `reqwest::Client` in six places (`commands/mod.rs:262,486`, `api_key.rs:136`, `query.rs:232`, `completions.rs:88`, `tui/client/admin.rs:56`); **MCP** in one (`lib.rs::sdk_client_for`). Both then call `Client::new_with_client`.
- **TS client** (`src/ui/src/api/gen`, hey-api `client-fetch`): `client.setConfig({...})` accepts a custom `fetch`; `client.ts` is the one configuration site. Raw `fetch` remains in `session.ts`, `tempo.ts`, `prom.ts`, `pyroscope.ts` (migration tracked by `ui-migrate-to-generated-sdk`). Views render `error.message` per panel; there is no shared error component.
- MCP `map_sdk_err` maps 429 → `internal_error("… rate limited, retry shortly")`.

## Goals / Non-Goals

**Goals:**

- One retry implementation per language, installed at client construction, invisible to call sites.
- Identical semantics across Rust and TS (what is retried, wait selection, bounds, fail-fast ceiling).
- Every consumer (CLI, MCP, UI) inherits it and reports exhaustion in its own idiom.

**Non-Goals:**

- Retrying Arrow Flight (SQL) calls in `signaldb_sdk::QueryClient` — gRPC has its own status semantics; out of scope.
- Circuit breaking, request hedging, client-side rate limiting.
- Migrating the UI's remaining raw-fetch callers to the generated SDK (they merely reuse the retrying fetch until `ui-migrate-to-generated-sdk` lands).

## Decisions

**D1 — Rust: override `ClientHooks::exec` via an xtask post-processing step, policy carried as progenitor's inner type.** `xtask generate` sets `with_inner_type(quote!(crate::retry::RetryPolicy))` (official setting; `new_with_client(baseurl, client, policy)`) and then rewrites the one generated line `impl ClientHooks<crate::retry::RetryPolicy> for &Client {}` into an impl whose `exec` calls `crate::retry::execute(self.client(), self.inner(), request, info).await`. The rewrite is a literal, asserted string replacement (xtask fails loudly if the line is not found), documented at the top of the generated file. _Alternatives:_ (a) wrap every generated builder — hundreds of call sites, drifts; (b) `reqwest-middleware` — cannot be injected into progenitor's `execute` path; (c) fork progenitor to add a `with_client_hooks` setting — right long-term, but blocks on upstream; the xtask rewrite is a 5-line, test-guarded shim we can delete when upstream lands (open a progenitor issue/PR as a task).

**D2 — Rust retry algorithm (`signaldb_sdk::retry`).** `RetryPolicy { max_attempts: 4, base: 250ms, per_attempt_cap: 10s, total_cap: 30s, retry_transient_idempotent: true }` + `RetryPolicy::disabled()`. `execute` loop: clone the request (`Request::try_clone()`; a streaming body that cannot be cloned is sent once, no retry), send, classify: `429` → retry (any method); `502/503/504`, `reqwest` connect/timeout errors → retry iff idempotent method; else return. Wait = `Retry-After` (seconds or HTTP-date, parsed by a tiny helper — no new dependency, `httpdate` is already transitively present via reqwest; if not, parse RFC 7231 with `chrono` which the workspace has) else `min(cap, base·2^n)·U(0,1)`. If `Retry-After > per_attempt_cap` or total would exceed `total_cap` → return the response now (fail fast). One `tracing::debug!(attempt, wait_ms, status)` per retry. Return the final `reqwest::Response`; progenitor then produces `Error::ErrorResponse(ResponseValue)` for 429, whose `.headers()` still carries `Retry-After` — `signaldb_sdk::retry::retry_after(&Error<E>) -> Option<Duration>` reads it for consumers.

**D3 — Rust: one builder.** `signaldb_sdk::ClientBuilder::new(base_url).bearer(token).tenant(t).dataset(d).timeout(dur).connect_timeout(dur).retry(policy).build() -> Client` owns the `reqwest::ClientBuilder` (default headers, timeouts) and passes the policy as inner. CLI's six sites and MCP's `sdk_client_for` collapse onto it. A test in each consumer greps its own source for `reqwest::Client::builder()` / `ClientBuilder::new()` and fails if found (same style as the existing parity checks).

**D4 — TS: a `retryingFetch` installed as hey-api's `fetch`.** `src/ui/src/api/http.ts` exports `retryingFetch(input, init, policy = DEFAULT)` implementing the same classification/wait rules (`Retry-After` header parse, jittered backoff, caps, `init.signal` respected via an abortable sleep). `client.ts` does `client.setConfig({ fetch: retryingFetch })`. The four raw-fetch files call `retryingFetch` instead of `fetch` (one-word change each; `ui-migrate-to-generated-sdk` deletes them later). Idempotency in TS is by method too, with an allowlist for read-`POST`s? — **No**: same rule as Rust (429 any method; transient only idempotent) to keep the contract identical; Query IR `POST`s therefore retry only on 429, which is the case that matters. `ApiError` gains `retryAfterMs` (from header or `retryAfterMs` body) and a throttling-specific `message` ("Rate limited — server asked to retry in 5 s") so the per-panel `error.message` renderers need no change. _Alternative:_ hey-api response interceptor — it cannot re-issue the request cleanly; custom `fetch` is the supported hook.

**D5 — TS: "retrying" visibility without touching every panel.** `http.ts` keeps a tiny observable `throttleState` (count of in-flight retries, last wait); the shell (`features/shell`) renders a single unobtrusive banner "Some requests are being retried after throttling…" while the count > 0. Panels keep their loading state naturally because the promise has not settled.

**D6 — CLI exit code `4` for throttled-after-retries; `--no-retry`/`SIGNALDB_NO_RETRY`.** Existing failures keep `1`; `4` is unused today. Retry note on stderr only when `stderr.is_terminal()`.

**D7 — MCP: throttled tool error.** `map_sdk_err` 429 arm → `ErrorData::new(ErrorCode(-32001?)…)`: keep JSON-RPC-safe by using `internal_error` code but a distinct message prefix `throttled:` and `data: {"retryAfterMs": N}` — rmcp exposes `ErrorData { code, message, data }`. Distinctness is by prefix + data, per the spec scenario.

**D8 — Parity assertion.** Extend the existing surface-parity test (tests-integration or the crate-level checks that back `client-surface-parity`) with: CLI and MCP crates contain no bare `reqwest::Client` construction; UI `client.ts` installs `retryingFetch`; and an end-to-end test that a router configured with `max_query_requests_per_sec = 1, burst_seconds = 1` serves 3 back-to-back SDK requests successfully (retry absorbs the 429s) and that `RetryPolicy::disabled()` sees the 429.

## Risks / Trade-offs

- [xtask string rewrite of generated code is a shim] → asserted at generation, covered by a test that the generated file contains the retry `exec`, and tracked upstream (progenitor issue) so it can be removed.
- [Retrying `429` on `POST` writes] → correct by HTTP semantics (429 = not processed) and SignalDB's limiter rejects before any handler runs; documented.
- [Default-on retry lengthens worst-case latency of failing calls] → caps (10 s per attempt, 30 s total) and fail-fast on long `Retry-After`; `--no-retry`/`RetryPolicy::disabled()` for callers that prefer immediacy.
- [Browser retries multiply load during an incident] → jitter + caps + `AbortSignal` on navigation; the server's own budget still governs.
- [Two implementations (Rust/TS) can drift] → both are table-driven from the same documented rules; a shared JSON fixture of (status, method, headers) → (retry?, wait) cases is run by both test suites.

## Migration Plan

Ship after `query-throttle-signalling`. No config migration; the CLI flag and env are additive. Rollback = revert; clients simply stop retrying.
